Xây nền tảng media với NestJS — Part 1: Nền móng, thiết kế CSDL & ACID

14 tháng 8, 2026 · Code thực chiến · Part 1/4

Bài này xây một thứ chạy được: nền tảng cho phép người dùng tải video lên, hệ thống tự chuyển mã ra nhiều độ phân giải, đẩy tiến độ về theo thời gian thực, rồi phát lại có tua được. Không phải một demo "hello world" gắn thêm vài thư viện — mà là hệ thống có tài khoản, có hạn mức, có tiền (credit), có hàng đợi và có nhiều tiến trình chạy song song.

Sở dĩ chọn đúng sản phẩm này là vì nó khiến những kỹ thuật thường bị dạy rời rạc trở thành bắt buộc. Bạn không thể chuyển mã video mà không đụng child_process. Không thể nhận file 2 GB mà không hiểu stream. Không thể để người dùng chờ ba phút mà không có realtime. Và không thể trừ tiền của họ mà không hiểu transaction.

🔍 Loạt bài này gồm 4 phần
Part 1 (bài này): kiến trúc, cấu trúc thư mục, chuẩn TypeScript, thiết kế cơ sở dữ liệu, TypeORM & migration, và ACID — kết thúc bằng việc tự tay tái hiện lỗi trừ tiền hai lần rồi vá nó.
Part 2: xác thực (JWT + refresh token có xoay vòng), API Gateway, giới hạn tần suất, nginx, và streaming upload/download.
Part 3: child_process chạy ffmpeg, worker_threads, cluster, hàng đợi và realtime.
Part 4: tách microservice bằng gRPC, cache, và vận hành.

1. Sản phẩm & kiến trúc

Trước khi gõ dòng code nào, cần thống nhất hệ thống gồm những gì và ai nói chuyện với ai. Đây là toàn cảnh sẽ được xây dần qua 4 phần:

⚠️ Cạm bẫy: để việc nặng chạy ngay trong request
Cách viết tự nhiên nhất là nhận file xong gọi luôn ffmpeg rồi trả kết quả. Nó chạy được trên máy bạn với một video 5 giây. Trên thật thì request treo vài phút, proxy timeout ở 60 giây, người dùng bấm lại, và bạn có hai tiến trình ffmpeg cho cùng một file. Ranh giới request nhanh — việc nặng ở nơi khác phải được vạch ngay từ kiến trúc, không phải sửa sau.

2. Cấu trúc thư mục

Toàn bộ dự án nằm trong một monorepo dùng npm workspaces. Lý do không phải "cho hiện đại", mà là ba service dùng chung định nghĩa .proto và chung một bộ kiểu dữ liệu — tách repo thì mỗi lần đổi một trường phải đồng bộ tay ba nơi.

Cấu trúc thư mục dự án 
nestjs-media-forge/
├── apps/
│   ├── gateway/          # NestJS HTTP + WebSocket — cửa vào duy nhất
│   │   └── src/
│   │       ├── main.ts
│   │       ├── app.module.ts
│   │       └── health/
│   ├── auth-svc/         # gRPC — tài khoản, JWT, refresh token
│   ├── media-svc/        # gRPC — job, metadata, sổ cái credit
│   ├── worker/           # KHÔNG phải HTTP — ăn hàng đợi, chạy ffmpeg
│   └── web/              # React + TypeScript + Tailwind
├── libs/
│   ├── proto/            # .proto dùng chung, sinh type cho cả 3 service
│   └── common/           # kiểu dữ liệu, lớp lỗi, tiện ích dùng chung
├── infra/
│   ├── nginx/            # reverse proxy, phục vụ file tĩnh, load balance
│   └── docker/           # docker-compose.yml + Dockerfile
├── tsconfig.base.json    # cấu hình strict dùng chung — mọi app kế thừa
└── package.json          # npm workspaces

Ba ranh giới đáng chú ý trong sơ đồ trên:

  • worker không mở cổng HTTP. Nó không phải service web, không có controller, không nhận request. Nó chỉ đọc hàng đợi. Nhầm chỗ này là bắt đầu chèn endpoint vào worker và mất luôn khả năng scale nó độc lập.
  • libs/proto là nguồn sự thật duy nhất của hợp đồng giữa các service. Không service nào tự định nghĩa lại kiểu của service khác.
  • infra/ tách khỏi code. Cấu hình hạ tầng thay đổi theo môi trường triển khai, không theo logic nghiệp vụ.

3. Chuẩn code & kiểu dữ liệu nghiêm ngặt

Phần này thường bị bỏ qua trong bài hướng dẫn, rồi trả giá ở phần sau. Đặt chuẩn trước khi có code thì rẻ; đặt sau khi đã có 5.000 dòng thì gần như không ai làm.

Bật "strict": true là điều kiện cần nhưng chưa đủ. Nó không bao gồm bốn cờ nguy hiểm nhất, và đó chính là bốn chỗ TypeScript hay cho cảm giác an toàn giả:

tsconfig.base.json 
{
  "compilerOptions": {
    "target": "ES2023",
    "module": "NodeNext",
    "moduleResolution": "NodeNext",

    "strict": true,

    // Bốn cờ KHÔNG nằm trong "strict" — đây mới là phần đắt giá
    "noUncheckedIndexedAccess": true,
    "exactOptionalPropertyTypes": true,
    "noPropertyAccessFromIndexSignature": true,
    "noImplicitOverride": true,

    "noImplicitReturns": true,
    "noFallthroughCasesInSwitch": true,
    "noUnusedLocals": true,
    "noUnusedParameters": true,

    "experimentalDecorators": true,
    "emitDecoratorMetadata": true,
    "skipLibCheck": true,
    "forceConsistentCasingInFileNames": true,
    "esModuleInterop": true,
    "resolveJsonModule": true
  }
}

Bốn cờ đó chặn cái gì? Đoạn dưới đây cố tình viết sai bốn chỗ. Với "strict": true đơn thuần, cả bốn đều biên dịch trót lọt:

probe.ts — bốn lỗi mà "strict" một mình không bắt 
// 1. Mảng rỗng vẫn trả về giá trị — lỗi kinh điển khi parse input
const ids: string[] = [];
const first: string = ids[0]; // thực tế là undefined lúc chạy

// 2. Gán undefined vào thuộc tính optional: "có key nhưng rỗng" khác "không có key"
interface Opts {
  readonly retries?: number;
}
const o: Opts = { retries: undefined };

// 3. Biến bắt lỗi mặc định là any — bạn có thể gọi bất cứ gì trên nó
try {
  /* ... */
} catch (err) {
  err.message; // err có thể là string, number, bất cứ thứ gì
}

// 4. Đọc biến môi trường không tồn tại mà không hề bị cảnh báo
const env: Record<string, string> = {};
const url = env.DATABASE_URL;

Với cấu hình ở trên, tsc chặn cả bốn:

Kết quả chạy thật: npx tsc --noEmit 
probe.ts(3,7):  error TS2322: Type 'string | undefined' is not assignable to type 'string'.
probe.ts(7,7):  error TS2375: Type '{ retries: undefined; }' is not assignable to type 'Opts'
                              with 'exactOptionalPropertyTypes: true'.
probe.ts(10,3): error TS18046: 'err' is of type 'unknown'.
probe.ts(14,17): error TS4111: Property 'DATABASE_URL' comes from an index signature,
                               so it must be accessed with ['DATABASE_URL'].
💡 Vì sao đáng chịu phiền ngay từ đầu
Ba trong bốn lỗi trên chính là ba loại bug sẽ xuất hiện ở các phần sau của loạt bài: ids[0] undefined khi parse metadata ffmpeg trả về, err kiểu unknown khi bắt lỗi từ tiến trình con, và biến môi trường thiếu khi chạy trong Docker. Bật cờ từ hôm nay thì trình biên dịch bắt; bật sau thì người dùng bắt.

Quy ước còn lại

  • Cấm any. Khi thật sự chưa biết kiểu, dùng unknown rồi thu hẹp bằng type guard. any tắt trình kiểm tra một cách âm thầm và lan sang mọi thứ nó chạm vào.
  • Dữ liệu vào từ bên ngoài luôn phải qua DTO + validation. Kiểu TypeScript biến mất lúc chạy; một interface không bảo vệ được gì trước request thật.
  • Một lớp lỗi thống nhất trong libs/common, không ném chuỗi, không ném object tuỳ hứng — Part 2 sẽ dùng nó để dựng bộ lọc lỗi cho toàn hệ.
  • Tên file kebab-case, một khái niệm một file, theo đúng quy ước NestJS: credit-ledger.service.ts, create-video.dto.ts.
